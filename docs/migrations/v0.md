# v0 Migration Guide

v0 系は breaking layout change を許容するが、長期互換 layer を増やさず migration item と CLI で移行する。

## M0-0001: Move legacy top-level paperops state into `_paperops/`

- Applies to: `_paperops/` internal layout checkpoint
- Status: CLI-backed
- CLI: `pops migrate apply M0-0001`

### Problem

旧 scaffold では `notes/`、`refs/`、`claims/`、`evidence/`、`workflow/`、`contracts/`、`review/`、`requests/` が project root にあり、人間が普段見る面と AI/ハーネス内部 state が混ざっていた。

このまま各 script / CLI が旧 top-level path を読み続けると、互換 fallback が増え続け、`paperops` の仕様が肥大化する。

### Migration

まず dry-run で確認する。

```sh
uvx --from paper-harness-cli pops migrate show M0-0001
uvx --from paper-harness-cli pops migrate apply M0-0001 --dry-run
```

問題なければ適用する。

```sh
uvx --from paper-harness-cli pops migrate apply M0-0001
```

移動対象:

- `contracts/ -> _paperops/contracts/`
- `workflow/ -> _paperops/workflow/`
- `refs/ -> _paperops/refs/`
- `evidence/ -> _paperops/evidence/`
- `claims/ -> _paperops/claims/`
- `review/ -> _paperops/review/`
- `requests/ -> _paperops/requests/`
- `notes/ -> _paperops/notes/`

`.pops/manifest.toml` がない project では、apply 時に manifest も作成する。

### Safety

- target path が存在しない場合だけ directory を rename する。
- source と target の両方が存在する場合は conflict として停止し、source は削除しない。
- dry-run は file system を変更しない。
- project 固有の card、notes、refs は中身を書き換えず、directory の位置だけを移す。

### After Migration

```sh
uvx --from paper-harness-cli pops doctor
make ci
```

この migration を含む checkpoint では script / CLI が旧 top-level path を一時的に読むことがある。次 checkpoint 以降では、`v0 -> next` chain でこの migration を踏んだことを前提に、legacy path fallback を削ってよい。

## M0-0002: Split managed defaults from project overlays

- Applies to: `_paperops/defaults/` managed default checkpoint
- Status: CLI-listed / update-paperops-backed
- CLI: `pops migrate show M0-0002`

### Problem

`_paperops/contracts/` と `_paperops/workflow/` に、paperops が配布・更新したい標準契約と、下流 project が論文固有に調整したい差分が混在している。

このまま同じ directory を managed update 対象にすると、project 側の最適化を保護しにくくなる。一方で既存 project の編集済み contract / workflow を自動で削除・移動すると、論文固有の判断を失う危険がある。

### Migration

この migration item は destructive move を行わない。まず managed default を追加する。

```sh
uvx --from paper-harness-cli pops update-paperops --plan
uvx --from paper-harness-cli pops update-paperops --apply
uvx --from paper-harness-cli pops migrate show M0-0002
```

新しい読み取り順:

1. `_paperops/contracts/<name>.yml` または `_paperops/workflow/<name>.yml` の project overlay
2. `_paperops/defaults/contracts/<name>.yml` または `_paperops/defaults/workflow/<name>.yml` の managed default
3. 互換期間中の legacy top-level path

既存の `_paperops/contracts/*.yml`、`_paperops/workflow/machine.yml`、`_paperops/workflow/focus-policy.yml`、`_paperops/workflow/subagent-roster.yml` は、review 済みになるまで project overlay として残す。

### Safety

- `pops migrate apply M0-0002` は file move を計画しない。
- `pops update-paperops --apply` は不足している `_paperops/defaults/` managed file を追加する。
- 既存の project overlay は自動削除しない。
- overlay を減らしたい場合は、defaults と内容を比較し、論文固有差分がないことを確認してから手動で削除する。

### After Migration

```sh
uvx --from paper-harness-cli pops doctor
make ci
```

次 checkpoint 以降では、contract / workflow kernel の managed update 対象を `_paperops/defaults/` に限定し、project overlay と state を自動上書きしない。

## M0-0003: Adopt the typed Results hierarchy model

- Applies to: typed editorial state checkpoint
- Status: CLI-listed / guide-only
- CLI: `pops migrate show M0-0003`

### Problem

新規 project は `pops init` で `_paperops/model/editorial/results-hierarchy.yml` の starter を受け取るが、既存 project は `storyline.md` の Results hierarchy を project 固有の editorial state として保持している。

この typed file は project-owned であり、`pops update-paperops` による managed update や migration の自動 move で上書きしない。compatibility checkpoint 中は legacy Markdown reader を維持するため、既存 project は手動移行を完了するまで旧 Results hierarchy を残せる。

### Migration

この migration item は file move を行わない。まず managed schema を受け取る。

```sh
uvx --from paper-harness-cli pops update-paperops --apply --only _paperops/defaults/schemas/
uvx --from paper-harness-cli pops migrate show M0-0003
```

次に、旧 Markdown の Results hierarchy を削除する前に以下を行う。

1. `_paperops/defaults/schemas/results-hierarchy.schema.json` と新規 project の starter model を参照し、project-owned の `_paperops/model/editorial/results-hierarchy.yml` を手動で作成する。
2. 旧 `storyline.md` の Results hierarchy にある各項目を、安定した ID と schema が要求する field を持つ typed entry へ移す。
3. `python scripts/check-section-contracts.py --root . --strict` を実行し、exit code 0 で strict checker が成功することを確認する。
4. strict checker 成功後にだけ、旧 Markdown の Results hierarchy を削除する。

### Safety

- `pops migrate apply M0-0003` は file move を計画しない。
- `_paperops/defaults/schemas/*` だけを paperops-managed update 対象とする。
- `_paperops/model/editorial/results-hierarchy.yml` は project-owned のまま保持し、自動追加・上書きしない。
- compatibility checkpoint 中は typed file を未採用でも legacy Markdown reader を利用できる。

### After Migration

```sh
make section-contract-check
```

`make section-contract-check` は日常確認用の advisory target である。legacy Results hierarchy を削除する gate には使わず、上記の明示的な `--strict` command を成功させる。

## M0-0004: Adopt the Editorial Model schema kernel

- Applies to: PaperOps 2 P1-A schema kernel checkpoint
- Status: CLI-listed / guide-only
- CLI: `pops migrate show M0-0004`

### Problem

P1-A は paperops-managed の `_paperops/defaults/schemas/registry.yml`、JSON Schema、checker を配布する一方、`_paperops/model/editorial/editorial-model.yml` と `results-hierarchy.yml` は project-owned state として保護する。したがって managed update や migration apply が欠損 model を自動生成してはならない。

### Migration

順序を変えずに次を行う。

1. `pops update-paperops --apply` で managed registry、schema、`scripts/check-paperops-models.py`、`make schema-check` を受け取る。
2. 新規 starter と schema を参照し、project-owned の `_paperops/model/editorial/editorial-model.yml` を手動で作る。既存 state からの自動 move、dual-write は行わない。
3. `make schema-check` で schema / references / semantics / hash phases を advisory に確認する。
4. `python scripts/check-paperops-models.py --root . --model editorial --strict` を実行し、schema、references、semantics が exit code 0 で成功することを確認する。成功した入力だけ canonical semantic-v1 hash を記録する。
5. 検査結果と Editorial Model の選択・棄却理由を人間が承認する。
6. strict command と人間承認の後にだけ Editorial Model へ authority を切り替える。

移行確認では `results_hierarchy.document` を project root 相対で解決するため、registry default と別の safe relative file を指定した場合もその exact file を用意する。fixture を `--document` で検査する場合は fixture directory 相対になり、`--results-document` は意図的な一時上書きにだけ使う。YAML timestamp / set / binary、非 string mapping key など JSON 非互換値は loader/hash が拒否するため、extension を含む全値を JSON 互換型へ直してから strict 検査する。
7. P2 の互換判断までは legacy controlled view を維持する。migration 中に legacy view を削除しない。

### Safety

- `pops migrate apply M0-0004` の `moves` は空で、欠損する project-owned model を作成も上書きもしない。apply は migration item の確認を進めるだけである。
- 成功した apply は `.pops/manifest.toml` の `[migrations].applied` に ID を記録する。dry-run と conflict は記録せず、適用済み ID の再実行は manifest を変更しない明示的 no-op になる。
- `make schema-check` は advisory であり、authority switch の gate は明示的な `--strict` command と人間承認である。
- P1-Bの六モデルkernelは提供済みだが、recordの自動生成、legacy card / TeXからのauthority switchは行わない。全model adoptionはM0-0005へ進み、P2 / P3 / P4のwriter切替まではlegacy authorityを維持する。

Task 4 を既存 project に取り込む場合は、先に `pops update-paperops --apply` で managed registry / schema / checker を更新し、必要なら新規 starterを参照して project-owned の `_paperops/model/manuscript/index.yml` を空 indexとして手動追加する。既存 section / blockを自動変換せず、TeX や legacy viewも削除しない。Manuscript checkerが strictで成功し、人間がauthority切替を承認するまではTeXを本文正本として維持する。

### After Migration

日常確認では `make schema-check` を使う。legacy controlled view の削除や dual-write は P2 以降の別 migration とする。

## M0-0005: Adopt the PaperOps 2 six-model kernel

- Applies to: PaperOps 2 P1-B six-model validation checkpoint
- Status: CLI-listed / guide-only
- CLI: `pops migrate show M0-0005`

Research、Editorial、Results hierarchy、Manuscript、Issue、Publication の六モデルを既存projectへopt-inするための案内である。M0-0005自体はguide-onlyのままでfile moveを行わない。P2では実作業を`pops model`へモデル化し、Agentがindex / hash / snapshotを手作業する必要をなくした。

1. `pops update-paperops --plan`でregistry、全schema、`paperops_schema.py`、`paperops_models.py`、checkerが同じupdateに含まれることを確認する。
2. `pops update-paperops --apply`でmanaged kernelだけを更新する。
3. `pops model status all`で六モデルのauthority modeと依存blockerを確認する。
4. 依存順に`pops model diff <model>`を実行する。変換不能fieldはlegacy sourceを直して再実行し、AIに架空値を補わせない。reportは`.paperops/migrations/<transaction-id>/report.json`で確認する。
5. `pops model validate <model> --strict`とreportを人間が確認する。問題なければ`pops model adopt <model> --dry-run`、続いて`pops model adopt <model> --yes`を実行する。
6. 戻す場合は`pops model rollback <model> --dry-run`で対象を確認してから実行する。v2 dependentがある場合だけ、意図を確認して`--cascade`を使う。
7. P2でauthorityを切り替えてもlegacy artifactを削除しない。P3のsection compiler / Writer packet、P4のworkflow writer cutoverは個別に承認する。

### Safety

- M0-0005はguide-onlyで`moves`を持たない。
- `pops update-paperops`は`_paperops/defaults/schemas/`と`scripts/`を管理し、`_paperops/model/`を追加・上書き・削除しない。
- legacy card、human-edited TeX、review/request、submission ledger、submitted snapshotをnever deletesとする。
- rollbackは新modelの参照を停止してlegacy authorityへ戻すことで行い、移行中のlegacy artifact自体は保持する。
- `diff`と`--dry-run`はtracked modelを変更しない。shadow / journalは`.paperops/migrations/`、snapshotは`.paperops/snapshots/`に置き、Git管理しない。
- adopt / rollbackはsource、candidate、current target、snapshotのhashが既知の場合だけ置換する。未知の手編集は`recovery.conflict`で停止する。
- Issueのraw reviewer textやlocal path、Publicationのartifact本体をmigration candidateへコピーしない。

## P1-B Task 3: Research managed-schema update note

Research Model の導入は destructive migration ではなく、managed schema/checker と新規 scaffold 用の空 project-owned starter を追加する checkpoint である。既存 project に `_paperops/model/research/index.yml` や Research record を自動生成せず、legacy `_paperops/claims/` / `_paperops/evidence/` card の authority も切り替えない。

既存 project へ取り込む場合は次の順序を守る。

1. `pops update-paperops --plan` で managed registry、`research-*.schema.json`、`scripts/paperops_models.py`、`scripts/check-paperops-models.py` が同じ update に含まれることを確認する。
2. `pops update-paperops --apply` で managed files を先に更新する。既存 project-owned state は上書きしない。
3. Research Model をまだ採用しない project は legacy card をそのまま保持する。空 starter や架空の CLM / RES / FIG / SRC / GATE record を埋める必要はない。
4. opt-in する場合だけ `_paperops/model/research/index.yml` を空 index から明示的に作成し、project-owned record を追加する。approval history は `/approvals` を除いた subject hash/revision への attestation とし、credential、raw path、実行 host を tracked record に入れない。
5. `python scripts/check-paperops-models.py --root . --model research --phase all` を実行し、人間が検査結果を承認する。legacy card の削除と authority switch は別 migration が定義されるまで行わない。

新規 `pops init` は架空 record を含まない `_paperops/model/research/index.yml` を配置する。既存 project と新規 project のどちらでも `make schema-check` は advisory のままであり、Research state を自動生成する writer としては動作しない。

## P1-B Task 5: Issue managed-schema update note

Issue Model は destructive migration ではない。新規 `pops init` は空の `_paperops/model/issues/index.yml` を配置するが、managed update と migration apply は欠損・編集済みの project-owned Issue index/recordを追加・上書きしない。既存 project は先に managed registry、`issue-*.schema.json`、checkerを更新し、必要な場合だけ空indexを手動追加する。P2のshadow migrationまではlegacy `_paperops/review/**` と `_paperops/requests/**` がwritable authorityであり、削除やdual-writeを行わない。

legacy field familyのdispositionは次のとおりである。

- feedback: `source` / `source_mode`、target、issue type / severity、upstream route / explanation、delegated role / subagent report、status、related cards、created / updatedを共通envelope、`{kind, id}` typed targets、delegation、metadataへ保持する。
- analysis request: request owner、claim/result/manuscript/panel refs、project link、requested output / verification axis、runops ID、freeze commit / data-not-seen、planned estimand〜QC、prediction / falsification / negative route、`xx` / figure / caption / claim replacement、execution commit / run / artifact / archive / result / figure provenance、reconciliation / gate rerun / human signoffを落とさない。acceptance criteriaはartifact refs、metric / estimand、denominator、unit of analysis、independence caveat、validated scope、not covered、provenance refs、result-card update refsをtyped objectで保持する。
- writing request: requester、target block、claim / feedback refs、claim / gate / allowed wording / forbidden overclaim、source language / JA-EN mirror / validationをtyped constraint / editing policyへ保持する。
- response: review round / feedback、resolution routeと説明、closure status / reason / next evidence / analysis request、changed claim / block / gate / result / source / figure / request、response-letter summaryを保持する。claim変更とscope変更は同一視せず、`scope_changed` が真の場合だけapproval refを要求する。
- review round: scope、artifact / feedback / report、review profile、summary、story / Results / Discussion / mismatch audit、delegated role / target / report / route recommendation / integration decision / reason、next routeを保持する。

tracked Issue recordには公開可能なsummaryとopaque local-reference IDだけを置く。raw confidential reviewer correspondence、narrativeへ埋め込まれたPOSIX / Windows local path、file / ssh / sftp URI、Authorization / API key / token / private-key PEMは拒否し、`_handoff/` やignored local stateに留める。closed responseは非空closure criteria、空のblocking dependency refs、audit refsとdependencyの両方にopen analysis requestがないことを要求する。`semantic.predicted_unresolved` はIssue単独ではwarning（strictではfail）であり、Publication dependencyに残る場合のerror昇格は後続Taskが担う。既存projectで採用する場合は `python scripts/check-paperops-models.py --root . --model issue --strict` と人間承認を終えるまでauthorityを切り替えない。

## P3 Task 4: Compile-context compatibility note

P3のtyped compile contextは追加的なread-only surfaceであり、既存TeX、mirror ledger、project-owned contractを移動・書換・削除しない。既存projectへ取り込む場合は`pops update-paperops --plan`でcheckpoint chainを、`pops update-paperops --dry-run`でmanaged file差分を確認する。release checkpointをまたぐ通常更新は`pops update-paperops --apply-chain`を使う。同じcheckpointで今回の変更を取り込む場合、既存managed filesは`changed`になるため、差分をreviewして上書きしてよいことを確認した後だけ`pops update-paperops --apply --force`を使う。単なる`--apply`はmissing fileだけを追加し、変更済みmanaged filesでは停止する。

更新対象は`_paperops/defaults/contracts/results.yml`、`discussion.yml`と、`scripts/mirror-check.py`、`mirror-freshness-check.py`、`check-submission-drift.py`、`check-citations.py`、`lint-bib.py`、`.agents/skills/sync-ja-en/scripts/sync_blocks.py`である。既存pathとcolonを含まないblock IDは引き続き有効で、TeXやledgerの手動migrationは不要である。更新後はcolon付き`% block:` IDも全mirror gateで同じIDとして扱われ、BibTeX registryはbrace形式とparenthesis形式のtop-level entryだけをauthority keyとして数える。

managed scriptを意図的にproject forkしている場合は`pops detach <managed-path> . --reason "<reason>"`で保護し、上記parser差分を手動統合する。`--force`でproject固有変更を失わないこと。`mirror-freshness-check.py --update`はこのmigrationでは自動実行せず、review済みJA/EN同期を記録するときだけ従来どおり明示実行する。
