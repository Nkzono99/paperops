# 図を設計し、描き、推敲する

論文の図は、読者に 1 つの比較をさせて、1 つのメッセージを渡すものです。手元の data を漏れなく載せた図は、
正確でも、どこを見ればよいかを読者に探させます。そこで、描く前に「何を読ませ、何を載せないか」を決め、
描いた後に「読者が実際に何を読んだか」を確かめます。最初に出てきた図は下書きです。
図 1 枚は `figures/<name>/` にまとめます。

```text
figures/<name>/
├── figure.md     設計（メッセージ、比較、描く量と形、載せないもの）、データ、推敲記録
├── make.py       縮約データを作り、図を描く
├── data/         縮約データ（図に必要な分だけ）、予想の図では予想の data
├── <name>.pdf    原稿用
└── <name>.png    確認用（掲載寸法）
```

## 手順

1. **描く前に、設計を `figure.md` に書く。** `figures/_template/` を `figures/<name>/` に複製し、`make.py` に
   手を付ける前に次を埋める。先に script を書くと、読めた data を全部描く方向へ流れる。
   既存の図に `figure.md` が無ければ、直す前に同じ項目を書く。

   - **メッセージ（1 文）**: 図を見た読者が言えること。結果を述べる文にする（「圧力損失の流量依存性」は題で、
     「粗い壁の管は、滑らかな管より圧力損失が 3 倍大きい」がメッセージ）。
   - **読者にさせる比較**: 何と何を見比べるとメッセージが読めるか。比較は 1 つに決め、主役の系列・領域を選ぶ。
     1 文に書けても、読むのに比較が 2 つ要るメッセージは 2 つの結果を含んでいる。図を分けるか、片方を本文に
     回すか、BRIEF の図の割り当てを見直す。
   - **描く量と形**: メッセージの文に出てくる量を、そのまま軸に置く。上のメッセージなら、縦軸は圧力損失で、
     線は粗い壁と滑らかな壁の 2 本になる。量が 3 つあるときは、比較で見比べる 2 つを軸に置き、残りの条件は
     線の名前にする。条件ごとの流速分布を並べると、読者が各 panel から損失を読み取り、頭の中で比べることになる。
     読者が頭の中で行うはずの計算（差、比、しきい値との比較）は、その結果を描く。値の大きさを判断する基準
     （しきい値、比べる相手）がメッセージに含まれるなら、基準を 1 つだけ図に置く。
     空間分布を載せるのは、メッセージが形や場所についてのものであるときで、その場合も代表の 1〜2 条件に
     とどめ、条件への依存は縮約した量の線で見せる。縮約した量は、区切り方（平均する範囲、しきい値）を変えても
     読み取りが変わらないことを確かめ、変わるなら分布のまま主役の領域に拡大して見せる。
     分布の図が言えるのは「どこに何があるか」までである。分布を足し合わせて決まる量（力、流束の合計など）に
     ついての結論は、分布の図のメッセージにせず、その量を計算して集約した図で言う。panel は、役割を 1 行で言え、それが無いとメッセージが
     読めないものだけを置く。
     形がすぐ決まる図は 1 行で足りる。主図や、分布と縮約量のどちらを見せるか迷う図は、候補を 2〜3 個、
     1 行ずつ書き、読者がメッセージに着くまでの手数が最も少ないものを選ぶ。決めかねたら、縮約データから
     両方を粗く描いて見比べる。
   - **載せないもの**: 手元にあるがこの図に入れないものと、その行き先（本文の 1 文 / Methods / 別の図 / 付録の図 /
     載せない）。典型は、確認のための系列（解像度や設定を変えた結果）、メッセージと別の発見、代表以外の条件、
     数値を伝えるだけの注記。要素を足すたびに主役が埋もれるので、削ることが、メッセージを見えるようにする
     いちばん大きな操作になる。迷うものは載せない側に置く。行き先を書いておけば、結果は図の外で読者に届く。
   - **支える発見、データの出典、掲載幅**: BRIEF の C1 など、source 名と run id、1 段か 2 段か。

   source の解析の図は、何が起きているかを作者が探すための図で、情報が多いほど役に立つ。論文の図は
   読者に説明するための図なので、解析の図をそのまま移さず、メッセージから設計し直す。

2. **データを縮約する。** `make.py` の `reduce()` が source から読み、設計で決めた量だけを `data/` に保存する。
   source の場所は `common.source("<name>")` で引く。run は run id で特定し、出典を `figure.md` に書く。
   run の出力を直接読む処理は重いので、計算機の決まりに従って計算ノードで実行する。
   縮約データがあれば、見た目の調整は手元ですぐ繰り返せる。

3. **描く。** `common.use_style()` を使い、掲載寸法（`common.SINGLE` / `common.DOUBLE`）で描き、
   `common.save(fig, __file__)` で保存する。Python は project の `.venv` を使う
   （無ければ `uv venv` と `uv pip install matplotlib numpy` で作る）。
   `save()` は、`figure.md` のメッセージと、読者が受け取る要素の数（panel ごとの線・色・注記・凡例の項目、
   最小の文字の大きさ）を表示する。線のそばに書いた名前は注記に、基準線は線に数える。
   次の手順で、メッセージと要素を並べて見るために使う。

4. **見て直す。** `<name>.png` を画像として開いて見る。下の観点を上から順に確かめ、問題を直して描き直す。
   これを 1 round として、`figure.md` の推敲記録に `- R1: 見つけた問題 → 変えたこと` と 1 行で残す。
   直すところが見つからなくなるまで続ける（少なくとも 2 round、多くて 5 round。手順 5 の初見の round も数え、
   既存の記録があれば番号を続ける）。
   直すときは、足す前に減らす。読み取りにくい所へ注記や panel を足すと、その分だけ読者の読む量が増える。
   まず主役以外を弱めるか除き、それでも読めないときに足す。足すのは、比較そのものを指す印（見比べる所に
   置く名前や記号、基準線 1 本）にし、説明の文は caption に書く。

   1. **メッセージと主役**: 5 秒見て、`figure.md` のメッセージが言えるか。読者にさせる比較が、図の中で
      いちばん目立つ要素になっているか。主役の系列には強い色と太い線を使い、脇役は灰色や細い線に落とす。
   2. **取捨**: `save()` が表示した要素を 1 つずつ見て、「これを消すと、メッセージが読めなくなるか」を問う。
      読めるままなら消すか、「載せないもの」に行き先を書いて移す。人が一度に見分けて覚えていられるのは
      4 つ前後なので、色で見分ける系列が 1 つの panel に 5 本以上ある図や、凡例・注記・panel が設計より
      増えている図は、手順 1 に戻って描く量と形を選び直す。数は目安で、決めるのは上の問いである。
   3. **読む手数**: 読者の目が行き来する所を減らす。凡例と線の往復は、線のそばに直接書く名前でなくす。
      見比べるものは同じ軸の上か隣り合う panel に置き、軸の範囲を揃える。同じ data を 2 つの形で描いて
      いたら、メッセージに近いほうを残す。対数か線形か、色の割り当て（量の大小は連続的な配色、正負は 0 を
      中心にした配色）がメッセージに合っているか。
   4. **掲載寸法での読みやすさ**: 文字が小さすぎないか（印刷で 7 pt 以上。`save()` が最小の大きさを表示する）、
      線や点が潰れていないか、label が data に重なっていないか、目盛が多すぎないか。
   5. **言葉**: 軸 label に量の名前と単位があるか。系列名は本文と同じ公開用の呼び名か
      （run id や変数名のままになっていないか）。panel が複数あれば (a), (b) を付ける。
   6. **図どうしの統一**: 同じ量・同じ条件には、全ての図で同じ色・記号・呼び名を使う。
      対応は `STYLE.md` の「図」に書いておく。
   7. **誠実さ**: 軸の切り方や配色が差を誇張していないか。主張が不確かさに左右されるなら、ばらつきを描く。
      誠実さのために要る要素は、主役より弱い見た目で残す。

5. **初見の目で確かめる。** 描いた本人はメッセージを知っているので、図を見返しても、伝わるかどうかと
   どこが余分かは判断できない。この会話と `figure.md` を見ていない agent（subagent）に PNG だけを渡し、
   次を尋ねる。

   ```text
   この画像だけを見て答えてください。他のファイルは開かないでください。
   1. この図が言っていることを 1 文で。
   2. それを読み取るために、図のどこを、どの順に見たか。
   3. 1 の読み取りに使わなかった要素（panel、系列、注記、凡例の項目）。
   4. 何を表すのか分からなかった要素、読み取りに迷った箇所。
   ```

   答えを `figure.md` の設計と比べ、食い違いの種類に合った所を直す。

   | 答え | 意味 | 直す所 |
   |---|---|---|
   | 1 がメッセージと違う、または弱い | 主役が目立っていないか、描いた量がメッセージの量ではない | 手順 1 の描く量と形 |
   | 2 が、決めた比較より長い道のりになっている | 見比べるものが離れている、凡例や軸を読み直させている | 観点 3 |
   | 3 に要素が挙がった | メッセージに要らない要素が載っている | 消すか「載せないもの」へ移す。読み取りを支える要素（軸、scale、色 bar）、誠実さのために要る要素、同じ data のうち切り離せない部分は、弱い見た目で残す |
   | 4 に要素が挙がった | 言葉か記号が読者のものになっていない | 軸・系列・記号の意味なら観点 5。3 にも挙がった要素は、説明を足さずに消す。対象や条件の説明は caption に書く |

   題や注記にメッセージを書いた図では、2 の道のりが data に届いているかを見る。読者が題を読んだだけなら、
   図はまだメッセージを裏づけて見せていない。
   推敲記録に `- R3（初見）: 読者の 1 文「…」、使わなかった要素 … → 変えたこと` と残す。直したら、新しい
   読者でもう一度確かめる（前の版を見た読者は初見ではなくなる）。2 回直してもメッセージが伝わらないときは、
   見た目ではなくメッセージか図の割り当ての問題として、BRIEF に戻る。round の上限に達して残った指摘は、
   著者への報告に書く。
   subagent が使えない環境では、`save()` の表示を上から読み、要素ごとに観点 2 の問いを立てる。
   初見の目より甘くなるので、その旨を著者への報告に書く。

6. **caption を書き、載せなかったものを行き先に届ける。** caption は原稿の figure 環境に書く（原稿がまだ
   無ければ `figure.md` に案を置く）。第 1 文でメッセージを言い、次に何が描かれているか、最後に条件を書く。
   本文からは、図を紹介する文ではなく、主張の文の根拠として参照する（「…3 倍大きい（図 2）」）。
   「載せないもの」の行き先に挙げた本文や Methods の文があることを確かめ、無ければ書く。
   図を分けた、panel を変えた、掲載幅を変えたときは、BRIEF の図の割り当てと、本文の参照（図番号、panel の
   記号）、原稿の `\includegraphics` の幅も合わせる。

7. **状態を進める。** 推敲が済んだら `figure.md` の状態を `reviewed` にして著者に見せる。
   その際、初見の読者が受け取った 1 文と、載せなかったものと行き先を 2〜3 行で伝える。載せなかったものを
   戻すかどうかは著者が決められる。著者が了承したら `approved` にする。

## 著者の指摘を反映するとき

指摘された図を直したら、同じ指摘が当てはまる他の図も直す。「見づらい」「情報が多い」「何を見ればよいか
分からない」という指摘は、色や文字の調整では直らないことが多いので、手順 1 に戻って描く量と形、載せないものを
決め直し、状態を `draft` に戻す。指摘が見た目の設定（文字の大きさ、色、線の太さ、余白）なら `figures/paper.mplstyle` か
`figures/common.py` に入れ、全ての図を描き直す。設定に落とせない好み（panel の並べ方、注記の入れ方、
載せるものの選び方）は `STYLE.md` の「図」に規則として書く。学習の手順は `paper-revise` に従う。

## 予想の図

結果がまだ無い図は、予想で描く。図があると、論文の流れと、その図を得るために要る計算がはっきりする。

- `make.py` の `PREDICTED` を `True` にし、`predict()` に予想の根拠（見積もりの式、既にある run からの外挿）を
  code として書いて `data/predicted.npz` を作る。根拠が code になっていれば、著者が予想の出どころを確かめられる。
- `common.mark_predicted(fig)` が図に PREDICTED の印を入れる。`figure.md` の状態は `predicted` にし、
  データの節に根拠を書く。
- 得られた結果と予想が 1 枚に混ざる図は、全体に印を入れる代わりに、予想の要素だけを `common.PRED_COLOR`
  （本文の `\pred{}` と同じ色）で描き、予想であることを線のそばの名前か凡例と、`figure.md` に書く。
  予想の要素が残る間、状態は `predicted` のままにする。
- 設計と推敲は、実際の data の図と同じに行う。結果が出たとき、data を差し替えるだけで済む。
- 結果が出たら `PREDICTED` を `False` にして `reduce()` で実際の data を読み、予想と見比べる。
  状態を `draft` に戻して推敲し直す。予想と違っていたら `paper-predict` の「結果が出たら」に進む。

## 模式図

概念や配置を示す模式図も、同じ手順で下書きを作る。「読者にさせる比較」には、読者が図から言えるべきこと
（配置、向き、定義）を書き、描く要素はそれを読むのに要る物だけに絞る。
模式図は仕上がりの差が出やすいので、下書きであることを著者に伝え、著者が描き直す場合の元になるよう、
要素と配置の意図を `figure.md` に書いておく。
