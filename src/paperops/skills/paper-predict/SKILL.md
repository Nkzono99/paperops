# 予想で先に書く

結果が揃ってから書き始めると、論文全体の流れが見えるのは最後になり、どの計算が本当に要るのかも
最後まで分かりません。そこで、ここでこういう結果が出て、こう解釈でき、論文にとってこういう意味を持つ、
という筋を結果より先に書き、あとから計算や実験で確かめます。予想が外れたら論文を直します。
手元の結果で言えることだけで原稿を閉じると、この進め方ができません。

予想は、予想だと分かる印（本文の `\pred{}`、BRIEF の発見と `figure.md` の状態）と、そう考える理由があれば、
作り話とは別のものです。予想するのは、これから得る結果です。実行済みの run、手元の data、文献が述べている内容は、
確かめたことをそのまま書きます。

## 手間を賭けの大きさに合わせる

計算資源も著者の時間も限られています。根拠を厳密にしていくと、制限が分かったり新しい物理が出てきたりしますが、
全ての予想にそれを行うことはできません。手間は、結果次第で論文の言うことが変わる所に使います。

- **当然の予想**: 外れたら物理より先に設定や code を疑う類のもの（保存則やスケーリングから決まる、
  既にある run の範囲の内側、よく知られた依存性）。理由を 1 行書けば足りる。確かめるための計算は立てず、
  図を作る計算の中で自然に確かめる。外れた場合の分岐は書かない。起こりそうにない結果への備えを並べても、
  言い訳を用意する以上の意味を持たない。
- **見込みの高い予想**: たぶん合っているが、値に幅がある。理由と幅を書く。図を作る計算がそのまま確認になる。
  分岐は書かない。
- **賭け**: どちらに転ぶか本当に分からず、それによって主張 1 文や発見の成否が変わる。ここにだけ、
  当たりの基準と、外れたら論文がどう変わるかを書き、検証を先に回す。

どれに当たるかは、次の 2 つを自分に尋ねて決める。

- この予想が外れたら、自分と著者は驚くか。驚くなら、分岐は要らない。
- 根拠をもう一段厳密にしたら、論文の言うことが変わりうるか。変わらないなら、今の根拠で足りる。

著者が「合っているはず」と述べた予想は、賭けとして扱わない。

## 予想を立てる

1. **言いたいことから逆に並べる。** BRIEF の主張 1 文を読者に納得させるには、どの結果を見せる必要があるかを
   並べ、既にあるものと無いものに分ける。無いものが予想の対象になる。手元の結果から言えることを積み上げるのではなく、
   言いたいことに必要な結果を先に決める。

2. **手元の結果を確かめる。** source の解析の `README.md` に加えて、`out/` にある小さな縮約出力（CSV、数十 KB の
   npz など）も読む。外挿の根拠はそこにあることが多い。読むための Python は project の `.venv` を使う。
   「確認済み」と呼ぶのは、source 側の判定（収束、定常、誤差の基準）を満たした結果にする。計算は終わったが
   判定を満たしていない値は、途中経過として値と時点を書き、最終的な値は予想として扱う。

3. **著者の見込みを先に使う。** 著者が会話で述べた見込みは、そのまま予想として採る。著者が触れていない所は
   自分で立て、一覧にして見せる。著者は一覧を直すだけで済む。

4. **具体的に書く。** 何が、どの向きに、どのくらい変わるかを書く。「増加すると考えられる」で止めない。
   値に幅があるものは代表値と幅で書く（「2.8 倍、幅 2〜3.5 倍」）。理由は、既にある run の傾向からの外挿、
   保存則やスケーリングによる見積もり、内容を確認できた先行研究、物理的な推論のどれかを、賭けの大きさに見合う
   長さで書く。

5. **新しい計算が要るものは、得られるかを見積もる。** いま使っている simulator と計算資源で出せるかを、
   source project の `cases/`、そこに配られている simulator の skill と文書、過去の run の `manifest.toml`
   （並列数、経過時間）から読み、次のどれかを書く。
   - 既にある出力の解析だけで出せる
   - 既にある run の継続で出せる
   - 既にある case の parameter を変えれば出せる
   - 新しい case が要る
   - simulator の改修が要る
   - 分からない

   見比べるのは、分解したい長さと格子幅、追いたい時間と時間刻み、定常や収束に達するまでの時間、領域の大きさ。
   そこから費用の見当（core-hours）を付ける。使いたい機能があるときは、文書の版と、導入されている simulator の版が
   合っているかも確かめる。分からない点は「分からない」と書く。改修が要る、または出せそうにない結果が主張の柱に
   なっているときは、別の確かめ方か主張の変更を著者と相談する。

6. **BRIEF に書く。** 発見の状態を `予想` にして、根拠にそう考える理由を書く。一部が手元にある発見は `一部確認` にし、
   根拠を「確認済み」と「予想」に分けて書く。賭けに当たる発見にだけ、確かめ方（当たりの基準を含む）と外れたらを足す。
   当たりの基準は、外れた場合の結果と区別できる線に置き、予定の計算の長さでその線に届くことを見積もる。段落骨子では、予想に依る段落の末尾に（予想）と付ける。

   ```markdown
   ### C2 圧力損失は、粗さの高さにほぼ比例して増える
   - 状態: 予想
   - 根拠: 粗さ 0.5% と 1% の run で比例している。2% は 2.8 倍（幅 2.5〜3.2 倍）と見る
   - 成立条件と置き場: 凹凸が粘性底層より高い範囲（Methods）

   ### C3 圧力損失の増加は、壁のせん断応力ではなく、凹凸の後ろの剥離で決まる
   - 状態: 予想（賭け）
   - 根拠: 粗さ 1% の run で凹凸の後ろに逆流が見える。応力の寄与は未評価で、どちらが主かは分からない
   - 成立条件と置き場: 凹凸の間隔が高さの 4 倍の配置（Methods と限界の段落）
   - 確かめ方: 既にある 3 run の壁面の力を、応力と圧力に分けて積分する（解析のみ）。圧力の寄与が 7 割を超えれば当たり
   - 外れたら: 応力が主なら、発見を「粗さは壁の実効的な面積を増やす」に変え、主張の機構の部分を書き換える
   ```

7. **主張 1 文が賭けに依っているなら、退避の主張を添える。** 強い主張を選んでよい。そのうえで、BRIEF の主張 1 文の
   下の行に、主張のどの部分が賭けかと、外れても手元の結果だけで言える主張を書く。著者は、賭けている所と、
   最悪の場合に残る論文を見て判断できる。賭けが無ければ、この行は要らない。

著者に「任せる」「確認は不要」と言われているときは、尋ねる代わりに、分からない点と判断が要る点を BRIEF の未決に書いて進める。

## 原稿に入れる

- **完成形の文で書く。** 結果が出たときに載せる文をそのまま書き、予想である部分を `\pred{...}` で囲む。
  結果に続く解釈と、論文にとっての意味の文も書く。Abstract と Discussion も同じに書く。
  「〜と期待される」「今後の課題である」と書くと、流れを完成形で読めず、結果が出たときに書き直しになる。
- **数値は `numbers.tex` で印を付ける。** マクロの定義の中に `\pred{}` を入れ、コメントに根拠を書く。

  ```tex
  % 予想: 粗さに比例するとした見積もり（BRIEF C2）。roughness-scan の再計算で置き換える
  \newcommand{\stressRatio}{\pred{2.8}}
  ```

- **図は予想で描く。** `paper-figure` の「予想の図」に従う。
- **`\pred` が無い project では preamble に足す。**

  ```tex
  \newcommand{\pred}[1]{\textcolor{orange!85!black}{#1}}
  ```

## これから要る計算を並べる

BRIEF の「これから要る計算」に、発表までに要る計算を表で書いて著者に見せる。この表が、発表を止めているものの
一覧になり、著者はこれを見て発表の時期を決める。載せるのは次の 2 種類。

- 主張 1 文と発見の言い切り文が使う結果のうち、まだ得ていないものを得る計算。主張や発見が機構を述べているなら、
  その機構を示す結果もここに入る。
- 賭けを確かめる計算。

どちらに入るかは、`\pred` が付いているかではなく、主張 1 文と発見の言い切り文がその結果を使うかで決める。
`一部確認` の発見では、言い切り文が使うのにまだ無い部分が対象で、既にある部分を延ばす計算（より長く、より多くの点で）は
次の節で分ける。計算の長さと点数は、主張が使う量（符号、大小、比）が決まる所までにする。

賭けを確かめる計算を先に置き、その中では主張 1 文への影響が大きく、費用が小さいものを先にする。当然の予想と
見込みの高い予想は、確かめるためだけの計算を足さない。費用が大きいか小さいかは著者の資源によるので、
合計を示して判断を仰ぐ。

| 順 | 何のため（発見・図） | 走らせるもの | 費用 | 賭けなら当たりの基準 |
|---|---|---|---|---|

run の作成と投入は source project の作業なので、その project の session にそのまま渡せる依頼文
（何を、何のために、どの出力が要るか）を表の下に添える。

## 上乗せの検証を分ける

確認済みの発見には、収束、感度、条件の拡張、別の手法との比較など、確かめられることがいくらでも見つかります。
思いついた順に表へ足すと、表は伸び続け、発表が遠のきます。主張を支える証拠が揃っていて、残っている疑いが
主張を覆すほどのものでなければ、検証を足すより発表を優先します。検証を思いついたとき、照合や初見の読者が
弱点を挙げたときは、次の 2 つを自分に尋ねて分けます。

- その疑いが当たっていたら、主張 1 文か発見の言い切り文はどう変わるか。変わり方を、機構つきで具体的に書けるか。
- 当たっていたら、自分と著者は驚くか。

| 答え | 扱い |
|---|---|
| 主張か発見が覆り、当たっていても驚かない | 賭けとして発見に書き、当たりの基準を付けて表に載せる |
| 主張の範囲が変わる（狭まる、広がる） | 計算は足さない。行った計算の範囲を、発見の成立条件に書く |
| 変わらない、変わり方を書けない、当たっていたら驚く | 行わない |

- 範囲が狭まると主張が読者にとって意味を失うなら、覆る場合として扱う。
- 主張の範囲そのものが未決のとき、著者と答えが割れそうなときは、分ける前に著者に尋ねる（BRIEF の未決）。
  範囲が決まれば、要る計算が決まる。広い範囲で言うと著者が決めたら、広げた分は検証ではなく発見の一部なので、
  予想の発見として載せる。
- 証拠が揃っていると言えるのは、主張の柱の発見が `確認済み`（source 側の判定を満たした結果）のときに限る。
  source に判定の基準が無いときは、主張が使う量がこの先の計算で変わらないと言える理由を、発見の根拠に 1 行書いて
  基準にする。柱の結果を分野の読者が信じるために当然求める確認（離散化への依存など）がどの条件にも無いときは、
  それも根拠の一部として表に載せる。1 つあれば、条件ごとには重ねない。
- 手元の出力の解析で数分で済む確認は、分けずにその場で行う。
- 成立条件は、行った計算の条件を述べる文で書く（「凹凸の形は 1 種類で計算した」）。行わないと決めた検証の結論を
  `\pred` で先に書いてあった文は、本文から外すか、この形に書き直す。
- 行わないと決めた検証は、表の下の「行わない検証」に 1 行ずつ、理由と行き先（成立条件に書く / 書かない）を
  付けて残す。著者が見て戻せるし、次の session や照合が同じ検証をもう一度持ち出さずに済む。

  ```markdown
  行わない検証:
  - 格子を 2 倍にした再計算: 粗さ 1% の run で格子を変えても損失は 2% しか動かず、3 倍という比は変わらない（書かない）
  - 凹凸の形を変えた run: 当たれば主張は「角ばった凹凸では」に狭まる。形は 1 種類で計算したと Methods と限界の段落に書く（成立条件に書く）
  ```

## 結果が出たら

1. **比べる。** source の `LOG.md` と解析を読み、予想と比べる。賭けは、結果を見る前に BRIEF に書いた
   当たりの基準で判定する。
2. **当たったら印を外す。** `\pred{}` を外し、`numbers.tex` に出典を書き、図を実際の data に差し替えて推敲し直す。
   BRIEF の状態を `確認済み` にし、根拠を実際の出典に書き換える。
3. **値だけ違ったら、値とそれに依存する文を直す。** 向きと解釈が同じなら筋は変わらない。比較や解釈の文が
   新しい値でも成り立つかを見直す。
4. **外れたら、まず種類を見分ける。** 当然の予想や見込みの高い予想が外れたときは、先に設定、解析、code を疑い、
   著者に伝える。賭けが外れたとき、または調べても結果が正しいときは、論文を直す。文章をぼかして結果に合わせることは
   しない。予想、結果、その差を `LOG.md` に記録し、主張と発見の変更案を著者に示す（`paper-brief` の
   「指摘を受けて直すとき」）。予想外の結果のほうが強い主張になることがあるので、その案も出す。
5. **報告する。** 発見ごとに、予想、結果、判定、原稿の変更を表で示し、残っている予想の数（`pops context`）を添える。
