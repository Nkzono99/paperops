# 予想で先に書く

結果が揃ってから書き始めると、論文全体の流れが見えるのは最後になり、どの計算が本当に要るのかも
最後まで分かりません。そこで、ここでこういう結果が出て、こう解釈でき、論文にとってこういう意味を持つ、
という筋を結果より先に書き、あとから計算や実験で確かめます。予想が外れたら論文を直します。
手元の結果で言えることだけで原稿を閉じると、この進め方ができません。

予想は、次の 4 つを備えていれば、作り話とは別のものです。

- **印**: 予想だと分かる（本文の `\pred{}`、BRIEF の発見と `figure.md` の状態）。
- **根拠**: なぜそうなると考えるか。
- **確かめ方**: 何を走らせ、何が出れば当たりか。
- **外れた場合**: 別の結果が出たら論文がどう変わるか。

予想するのは、これから得る結果です。実行済みの run、手元の data、文献が述べている内容は、
確かめたことをそのまま書きます。

## 予想を立てる

1. **言いたいことから逆に並べる。** BRIEF の主張 1 文を読者に納得させるには、どの結果を見せる必要があるかを
   並べ、既にあるものと無いものに分ける。無いものが予想の対象になる。手元の結果から言えることを積み上げるのではなく、
   言いたいことに必要な結果を先に決める。

2. **手元の結果を確かめる。** source の解析の `README.md` に加えて、`out/` にある小さな縮約出力（CSV、数十 KB の
   npz など）も読む。外挿の根拠はそこにあることが多い。読むための Python は project の `.venv` を使う。
   「確認済み」と呼ぶのは、source 側の判定（収束、定常、誤差の基準）を満たした結果にする。計算は終わったが
   判定を満たしていない値は、途中経過として値と時点を書き、最終的な値は予想として扱う。

3. **著者の見込みを先に使う。** 著者が会話で述べた見込みは、そのまま予想として採る。著者が触れていない所は
   自分で立て、一覧にして見せる。著者は一覧を直すだけで済む。

4. **具体的に書く。** 何が、どの向きに、どのくらい変わるかを、代表値と幅で書く（「2.8 倍、幅 2〜3.5 倍」）。
   「増加すると考えられる」で止めない。幅は、根拠から正直に言える範囲にする。根拠は、強い順に次から選んで書く。
   - 既にある run の傾向からの外挿
   - 保存則、スケーリング、解析的な見積もり
   - 先行研究の結果（実在と内容を確認できた文献）
   - 物理的な推論

   あわせて確信度（高・中・低）を付ける。1 つの発見の中で確信度が分かれるときは、部分ごとに書く。

5. **得られるかを見積もる。** 予想した結果が、いま使っている simulator と計算資源で出せるかを調べる。
   source project の `cases/`、そこに配られている simulator の skill と文書、過去の run の `manifest.toml`
   （並列数、経過時間）を読んで、次のどれかを書く。
   - 既にある出力の解析だけで出せる
   - 既にある run の継続で出せる
   - 既にある case の parameter を変えれば出せる
   - 新しい case が要る
   - simulator の改修が要る
   - 分からない

   見比べるのは、分解したい長さと格子幅、追いたい時間と時間刻み、定常や収束に達するまでの時間、領域の大きさ。
   そこから費用の見当（core-hours）を付ける。使いたい機能があるときは、文書の版と、導入されている simulator の版が
   合っているかも確かめる。分からない点は「分からない」と書く。改修が要る、または出せそうにない結果が主張の柱に
   なっているときは、別の確かめ方か主張の変更を著者と相談する。

6. **当たりの基準と、外れた場合を書く。** 当たりの基準は、外れた場合の結果と区別できる線に置く
   （どちらの結果でも満たせる基準にしない）。外れた場合は、ありそうな別の結果を 1〜2 個挙げ、そのとき論文が
   どうなるかを書く（主張が変わる、発見を落とす、限界として書く、むしろ強い主張になる）。

7. **BRIEF に書く。** 発見ごとに、状態を `予想` にして、根拠・確かめ方・外れたらを埋める。一部が手元にある発見は
   `一部確認` にし、根拠を「確認済み」と「予想」に分けて書く。段落骨子では、予想に依る段落の末尾に（予想）と付ける。

   ```markdown
   ### C2 圧力損失の増加は、壁のせん断応力の増加で説明できる
   - 状態: 予想（確信度: 中）
   - 根拠: 粗さ 1% の run でせん断応力が滑面の 1.8 倍。粗さに比例すると見て、粗さ 2% では 2.8 倍（幅 2〜3.5 倍）
   - 成立条件と置き場: 凹凸が粘性底層より高い範囲（Methods）
   - 確かめ方: roughness-scan の case に壁面応力の出力を足し、粗さ 0.5, 1, 2% で再計算（各 256 並列・12 h）。
     応力から求めた圧力損失が、計算の値と 2 割以内で合えば当たり
   - 外れたら: 応力で足りない場合、凹凸の後ろの剥離による圧力抵抗が効いている。発見を「応力と圧力抵抗の両方」に変える
   ```

8. **主張が予想に依っているなら、退避の主張を添える。** 強い主張を選んでよい。そのうえで、BRIEF の主張 1 文の
   下の行に、主張のどの部分が予想に依っているかと、予想が外れても手元の結果だけで言える主張を書く。
   著者は、賭けている所と、最悪の場合に残る論文を見て判断できる。

著者に「任せる」「確認は不要」と言われているときは、尋ねる代わりに、分からない点と判断が要る点を BRIEF の未決に書いて進める。

## 原稿に入れる

- **完成形の文で書く。** 結果が出たときに載せる文をそのまま書き、予想である部分を `\pred{...}` で囲む。
  結果に続く解釈と、論文にとっての意味の文も書く。Abstract と Discussion も同じに書く。
  「〜と期待される」「今後の課題である」と書くと、流れを完成形で読めず、結果が出たときに書き直しになる。
- **数値は `numbers.tex` で印を付ける。** マクロの定義の中に `\pred{}` を入れ、コメントに根拠を書く。

  ```tex
  % 予想: 粗さに比例するとした見積もり（BRIEF C2）。roughness-scan の再計算で置き換える
  \newcommand{\stressRatio}{\pred{2.8}}
  ```

- **図は予想で描く。** `paper-figure` の「予想の図」に従う。
- **`\pred` が無い project では preamble に足す。**

  ```tex
  \newcommand{\pred}[1]{\textcolor{orange!85!black}{#1}}
  ```

## 検証の順番を決める

予想を、主張 1 文への影響が大きく、確信度が低く、費用が小さいものから順に並べ、BRIEF の「検証の順番」に表で書いて
著者に見せる。費用が大きいか小さいかは著者の資源によるので、合計を示して判断を仰ぐ。

| 順 | 発見 | 走らせるもの | 当たりの基準 | 費用 | 外れたら |
|---|---|---|---|---|---|

run の作成と投入は source project の作業なので、その project の session にそのまま渡せる依頼文
（何を、何のために、どの出力が要るか）を表の下に添える。

## 結果が出たら

1. **比べる。** source の `LOG.md` と解析を読み、予想ごとに、BRIEF に書いておいた当たりの基準と比べる。
   基準は結果を見る前に書いたものを使う。
2. **当たったら印を外す。** `\pred{}` を外し、`numbers.tex` に出典を書き、図を実際の data に差し替えて推敲し直す。
   BRIEF の状態を `確認済み` にし、根拠を実際の出典に書き換える。
3. **値だけ違ったら、値とそれに依存する文を直す。** 向きと解釈が同じなら筋は変わらない。比較や解釈の文が
   新しい値でも成り立つかを見直す。
4. **外れたら、論文を直す。** 文章をぼかして結果に合わせることはしない。予想、結果、その差を `LOG.md` に記録し、
   BRIEF の「外れたら」をもとに主張と発見の変更案を著者に示す（`paper-brief` の「指摘を受けて直すとき」）。
   予想外の結果のほうが強い主張になることがあるので、その案も出す。
5. **報告する。** 発見ごとに、予想、結果、判定、原稿の変更を表で示し、残っている予想の数（`pops context`）を添える。
